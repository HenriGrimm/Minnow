1What Minnow is

Minnow is a local-first development workspace: a single desktop app that gives an AI assistant a full set of developer tools — reading and writing files, running git, spawning a terminal, indexing your code, searching the web, and keeping a persistent memory — all working against the project folder you have open.

The important word is local-first. Minnow does not ship with an AI model and it does not run its own model in the cloud by default. Your code, your chats, your memory, and your settings all live on your machine (in a folder called ~/.minnow). The only thing you have to supply is a model to talk to — and that model can be local or in the cloud, your choice.

Three things stacked together

Minnow is really three layers, and understanding the layers explains almost everything about the product:

LayerWhat it does
A workspace shellThe app UI. You pick a project folder, then work in Code with chat beside your files. Other apps (Research, Models, Brain, Issues…) hang off the same shell.
A local tool serverA Node process on port 9473 that does everything a browser tab can't: read/write files, run git, open terminals, index code, store chats, download models. It binds to loopback only.
A model you supplyAny OpenAI-compatible endpoint — LM Studio, Ollama, a model Minnow serves itself, or a cloud API. Minnow is indifferent to where it lives.
💡 The one-sentence version

Minnow is the environment (files, git, terminal, memory) that makes an AI assistant genuinely useful for development, and it keeps that environment on your machine.

What Minnow is not

  • It is not a chatbot website. It has no account, no cloud backend for your code, and no telemetry.
  • It does not include a model. If nothing can answer you, it's almost always because no model is connected and running.
  • It is not a general-purpose code editor replacement — the chat is the product, and the file tree/editor/preview around it exist so the assistant has real things to act on.

2The mental model

Read this once and most of Minnow stops needing explanation. Two ideas do most of the work.

Idea 1 — The loop

Every time you press Enter, this is what happens:

  1. Minnow assembles a system prompt — the active mode, your standing rules, retrieved memories, and guidance for using tools.
  2. It sends your conversation history plus the tool definitions your mode allows to the model.
  3. The model streams a reply. If it wants to call a tool, Minnow checks each one against your permissions and either runs it, asks you, or refuses.
  4. Tool results go back to the model, and it continues. This repeats until it stops calling tools.
  5. The finished turn is written to disk.

Two consequences explain most "why did it do that?" moments:

  • A model that can't call tools can only talk. If the assistant is confidently reciting answers but never actually reads a file, the model (not your permission settings) is the likely cause.
  • Every tool result costs context. Reading a huge file isn't free — it competes with your conversation for space in the model's window.

Idea 2 — The workspace boundary

File, git, search, and terminal tools resolve under one folder: the project you opened. An attempt to read outside that folder fails. That boundary is the single most important safety property in Minnow — it's what stands between an over-eager assistant and the rest of your disk. You can deliberately lift it (full-disk access), but that's a conscious decision, not a default.

📐 Why this matters for you

When you open a repo in Minnow, think of it as handing the assistant a sandbox that is exactly the size of that repo. Everything it can touch is in there; everything it can't touch is outside it. That mental picture makes the rest of the guide predictable.

3Core concepts

These are the words you'll keep hearing. Learn them and everything else has a place to attach.

Workspace
The project folder you open. It becomes the root that all file/git/terminal tools operate inside. You can switch it anytime from the menubar.
Mode
A preset that changes two things at once: the system prompt the model gets and which tools even exist for that turn. There are four in the composer: General, Build, Plan, Debug.
Tool
A function the model may call — read a file, run a command, search the web, write a memory page. Minnow ships over a hundred of them.
Permission level
Every tool is Off, Ask, or Full — see section 7.
Provider / Model
A provider is an endpoint you connect to (LM Studio, Ollama, OpenAI, etc.). A model is a specific model that provider reports. You pick providers, then pick a model for a chat.
Context window
The model's finite working memory for one conversation. System prompt + rules + memories + tools + your whole history + tool results all compete for it.
Brain (memory)
A real wiki of markdown pages on your disk. Minnow retrieves relevant pages before a turn and injects them, so the assistant can remember durable facts across chats.
Rule
A standing instruction injected into every prompt ("always run tests before committing"). Off by default; costs context every turn.
Skill / slash command
Packaged instructions the model follows when you type / — code review, commit messages, a UI critique, etc.
Sub-agent
A nested agent the main assistant can spawn for parallel work (a researcher, an explorer) that reports back without cluttering your transcript.
🔗 Apps are surfaces, not silos

Code, Research, Brain, Issues, and the rest all share one chat engine, one set of tools, one session store, and one workspace. Opening Research doesn't start a different assistant — it gives the same assistant a different layout. That's why work can flow freely: an issue can be sent to a chat, a research report can be discussed, a plan can become a board of tasks.

4Getting started

Four steps from zero to a working assistant. Total time is mostly the model download.

1

Install Minnow

Download the installer for your platform from the Minnow releases page:

  • Windows — an NSIS .exe installer. If SmartScreen warns the publisher is unknown, choose More info → Run anyway (builds may be unsigned).
  • macOS — a .dmg (or .zip).
  • Linux — an AppImage; make it executable and run it.
2

Open a project folder

On first launch, Minnow opens on the workspaces picker. Choose the folder of the project you want to work on. Minnow then opens Code with the chat rail on the left, beside the files it will work on. That folder is now your workspace boundary.

Behind the scenes, Minnow creates its home folder (~/.minnow or %USERPROFILE%\.minnow) and starts the local tool server on port 9473.

3

Connect a model

Pick whichever route fits you:

If you want…Do this
A local model you already haveLM Studio (start its local server, default http://localhost:1234) or Ollama (http://localhost:11434).
Minnow to download & serve itModels → Recommendations probes your hardware and scores models that will fit, then Library downloads and Serve runs it.
Frontier quality, no local hardwareModels → Providers has one-click presets (OpenAI, Anthropic, OpenRouter, Groq, …) plus a custom base URL. You paste an API key.

All of this lives in the Models app. If a provider is already listening on its default port, Minnow detects it automatically.

4

Pick a model and go

There are two pickers, and mixing them up causes a lot of "why is it using the wrong model?" confusion:

  • Menubar model chip — the global default for new chats.
  • Composer picker (or Ctrl+M) — binds a model to this chat only.

If the picker is empty: is the provider running? Is a model loaded in it? Is the base URL right (including /v1 where needed)? Then press Refresh in Models → Providers.

💡 First-run wizard

You'll usually get a short guided setup — theme, provider, model, tool permissions, and memory. Skip it any time and re-run it later from Settings → General → Run setup again.

Closing and quitting

Closing the window does not quit Minnow. By default it hides to the system tray so chats, agents, scheduled jobs, and the tool server keep running — a long agent run should survive you closing the window. Use Quit Minnow from the tray for a full shutdown. Change this under Settings → General → Desktop app.

5Your first real turn

Let's do one full turn and notice each piece, so the abstract terms have a concrete memory attached.

The layout you're looking at

AreaWhat it is
App rail (left edge)Switch between Code, Research, Models, Brain, Issues, Scheduler.
Menubar (top)Workspace chip, model chip, notifications, Settings, help.
Chat rail (inside Code, left)Your conversations. Search and start new chats here.
Composer (centre)Where you type. Mode strip, attachments, tools, model, send.
Project panel (right)File tree, editor, preview — everything scoped to your folder.

Send something that forces Minnow to do something

Type into the composer and press Enter (Shift+Enter for a new line). Try a question that makes the assistant actually look at something instead of reciting from memory:

What can you do on this machine? Check what tools you have.

While it streams you'll see a live tokens/second readout. Press Enter again or the stop button to cut it short — the partial reply stays.

Approving a tool

Most interesting requests make the model call a tool. When a tool's permission is Ask, a strip appears in the chat with three choices (and keyboard shortcuts):

KeyAction
1Allow once
2Always allow this tool (a permanent settings change — see section 7)
3Cancel
⚠️ "Always allow" is permanent

Pressing 2 writes a real permission change to disk and applies to every future chat, not just this one. That's usually what you want for a read-only tool like read_file on day two, and almost never what you want for execute_command. If you change your mind, Settings → Integrations → Tools.

The context ring

The ring beside Send shows how much of the model's context window this conversation is using. Click it for a breakdown. If replies suddenly get vague or start forgetting things, this ring is the first place to look (see section 8).

6Choosing modes

A mode is the most consequential control in the composer, and it's one click. It changes the system prompt and the tool list. Pick the mode before you send — it decides what's even possible for that turn.

ModeUse it forKey difference
GeneralEveryday questions, mixed tasks, draftingBroad tools with normal approvals. The only composer mode that can read the Minnow manual.
BuildWriting code in your open projectThe development default: files, git, terminal, code intelligence, sub-agents, browser automation.
PlanDesigning and analysing without actingReads anything and can run shell commands to investigate, but the mutating file/git tools are removed. Can only write plan documents under documentation/plans/.
DebugChasing failures, reading logsEverything Build has, plus local diagnostics, aimed at the Issues tracker.
💡 Plan mode is a real guard, not a request

"Design this, don't touch my code" in Plan mode isn't a plea — the editing tools literally aren't in the payload the model receives. That's why "Plan" is the safe mode for exploring a big idea before you commit to implementation.

A quick decision table

  • Asking how something works / drafting text → General
  • Implementing a feature in your open project → Build
  • Writing a spec you don't want acted on yet → Plan
  • Chasing a bug and filing what you find → Debug

You can switch modes mid-conversation; it takes effect from the next message.

7Tools & permissions

Tools are what make Minnow useful and what make it risky. The permission system is how you keep the first without the second.

Three permission levels

LevelBehaviour
OffThe model never sees the tool. It can't call it, and it costs no context.
AskThe model may call it; you approve each call from the strip in chat.
FullRuns immediately, no prompt.

Set them in two places that write to the same file:

  • Settings → Integrations → Tools — the full catalog grouped by category, with bulk actions.
  • The tools button in any composer — the same Off/Ask/Full controls in a popover, right in your chat.

What's on by default

Minnow ships conservative. A fresh install enables roughly thirty tools; the rest are Off. A few safe ones default to Full (read-only or clearly safe): Brain/memory tools, Minnow documentation, and settings reads. Everything else that's enabled starts on Ask — files, git, shell, and browser tools all need your say-so until you decide otherwise.

Two gates, not one

A tool must pass both of these, in order:

  1. The mode must allow the tool at all.
  2. Your permission for it must be Ask or Full (not Off).

So turning a tool to Full does not make it available in Plan mode (Plan removed it), and a mode allowing a tool doesn't skip your approval. Modes are a ceiling, not a grant.

🛡️ The shell is special

File and git tools are confined to your workspace boundary. But execute_command on Full is different: once the model is inside a shell, the path check never sees the command string, so it has the same filesystem authority as you. If you're letting an agent run commands unattended, consider the agent shell sandbox (Settings → General).

A sensible starting setup

Cautious (best default for most people): read-only tools on Full (read_file, list_directory, grep, git_status, git_diff), and everything that writes or executes on Ask. The model stops nagging about harmless lookups, and you still see every mutation.

8Memory, context & rules

A model has no memory. Every turn, Minnow rebuilds everything it knows and sends it. Three separate mechanisms feed that rebuild — and confusing them is the #1 cause of "the assistant has amnesia."

MechanismQuestion it answersWhere it lives
Context windowWhat's in this conversation right now?In the request, rebuilt every turn
Memory (Brain)What did we establish days ago?On disk, retrieved when relevant
RulesWhat must always be true of my behaviour?On disk, injected every turn

The context window

Everything competes for that finite space: system prompt, rules, retrieved memories, tool definitions, your whole history, and every tool result. A single large file read can cost more than an hour of conversation. The context ring is your gauge.

When the window gets full, the symptoms are distinctive: the model forgets a constraint you set, repeats work, or answers a question from ten messages ago. Fixes, cheapest first:

  1. Start a new chat for the new subtask (usually right).
  2. Remove large attachments you no longer need.
  3. Move durable facts into Brain, then start fresh — they come back via retrieval, not scrollback.
  4. Switch to a larger-context model.

Memory = Brain

Memory in Minnow isn't a hidden vector blob — it's a real wiki of markdown pages in your Minnow home that you can open, read, edit, and delete. When memory is on, Minnow retrieves relevant pages before a turn and injects them. You can save a memory three ways: ask ("remember we deploy on Fridays"), write a page yourself in Brain → Edit, or let Minnow propose one from your conversations (they queue in Brain → Proposals for review).

Good memory: durable decisions and their reasons, conventions, environment quirks, "we tried X and it failed because Y." Bad memory: transcripts, anything that changes weekly, secrets.

Rules

Rules are standing instructions injected into every system prompt: "Always use TypeScript strict mode." "Never commit without running tests." They're in Settings → Agents → Rules, off by default, and grouped so you can enable/disable a whole set together. Keep them short and testable — they cost context on every turn.

⚠️ Memory is retrieved into prompts

That includes prompts sent to a cloud provider if that's what you're using. Don't put secrets in memory.

9Skills & slash commands

Type / at the start of an empty composer to open the picker. Skills are packaged instructions the model follows — code review, commit-message writing, a security pass, a UI critique. A dozen or so ship built in and are on by default, and you can install more from the Skills Library.

The same picker also holds two chat controls that aren't skills:

  • /goal — keeps working until a condition is met.
  • /loop — re-runs a prompt on a schedule.
💡 Example

Before committing, type / and pick the commit-message skill. The assistant drafts a conventional commit message from your staged diff instead of guessing from memory.

10The other apps

Everything shares one assistant, one tool set, one session store. These are different surfaces of the same brain:

AppWhat it's for
CodeThe primary surface. Chat beside your files, editor, preview, terminal.
ResearchHand a question to a research agent that runs multiple rounds and writes a report.
ModelsProviders, model library, routing, sampler, usage & cost.
BrainYour memory wiki — browse, edit pages, run lint to find orphans and contradictions.
IssuesA Linear-style tracker (list + board) where the assistant can file and work bugs.
SchedulerScheduled, unattended agent runs.
SettingsGeneral, appearance, providers, tools, agents, rules, and more.

The assistant can also open an app on its own when it decides that's the right move — that's the launch_minnow_app tool, and it can carry your message across as a seed.

Routing (in Models)

You can bind different models to different jobs: a small fast local model for naming chats and routine turns, a bigger cloud model for planning and review. A 3B model is fine at titling a chat; you don't want it judging whether your goal was met. This lives under Models → Routing.

11Practical workflows

Concrete sequences to build muscle memory.

Understanding an unfamiliar codebase

  1. Open the repo, pick General (or Build).
  2. "Give me a tour of this project: entry points, main modules, and where the config lives. Read the actual files — don't guess."
  3. Approve the read tools. Follow up on the parts you don't get.

Implementing a feature safely

  1. Plan mode first: "Design the change. Don't touch any code." — read the plan doc it writes under documentation/plans/.
  2. Switch to Build: "Implement the plan, run the tests, and show me the diff."
  3. Commit before long runs — Minnow's undo can restore a working tree, but a commit is cheaper and more certain.

Chasing a bug

  1. Debug mode: "This endpoint 500s under X. Read the logs and the relevant code, reproduce if you can, and file what you find in Issues."
  2. Debug mode is the only composer mode that can read local diagnostics.

Keeping knowledge for next time

  1. Mid-conversation: "Remember that we deploy on Fridays and that CI is flaky on Windows." → the assistant saves a Brain page and shows a 10-second review card you can reject or open.
  2. Next week, in a fresh chat, the relevant page is retrieved automatically.

Attachments (when you do want them)

Drag files onto the composer (up to 10 MB each). Images need a vision model; PDF/Word/Excel are parsed to text first. For code, you usually don't want an attachment at all — keep the project open and let the model read the specific files it needs with tools.

12Safety & privacy

  • Local by default. Chats, memory, API keys, downloaded models, and logs all live in your Minnow home. No analytics, no crash-reporting service.
  • Traffic leaves only when you send it somewhere — a cloud provider you configured, a web search, a page fetch, a model download.
  • Secrets are encrypted at rest with AES-256-GCM under a key file in your Minnow home. If you lose that key file, the keys can't be decrypted.
  • The workspace boundary confines file/git tools to your open project. Lifting it to full-disk is a deliberate choice.
  • Content the model reads is data, not instructions. Web pages and fetched documents are wrapped in untrusted-content fences, so a page saying "ignore your instructions" arrives as quoted material, not a command. It mitigates prompt injection — it doesn't make it impossible — so be thoughtful about pairing Full tools with a model that reads arbitrary web pages.

13Glossary (cheat sheet)

OpenAI-compatible
An API shape (/v1/chat/completions) that many providers speak. Because Minnow targets it, one app can drive dozens of backends.
Provider
The endpoint you connect to (LM Studio, Ollama, OpenAI, …). You manage these in the Models app.
Model
A specific model a provider reports. Picked per-chat or as the global default.
System prompt
The standing instructions assembled before each turn from mode + rules + memory + tool guidance.
Streaming
The model's reply arriving token-by-token in real time, with a live speed readout.
Sub-agent
A nested agent for parallel work that reports back without cluttering the main transcript.
Work agent / Board
Delivery agents (builders, testers, fixers) each working one task on a kanban board.
Token
The unit of context. Roughly a word or a chunk of a word; the context ring and budgets are measured in these.

14Troubleshooting

Nothing answers me

  1. Is your model provider actually running, with a model loaded?
  2. Models → Providers — is the base URL right? Press Refresh.
  3. Settings → Advanced → Health & diagnostics — subsystem probes, grouped errors, and a local log tail. Copy report makes a redacted summary for a bug report.

The model picker is empty

  1. Is the provider process running?
  2. Is a model loaded in it? Minnow lists only what the provider reports.
  3. Is the base URL right, including /v1 where required?
  4. Press Refresh.

Replies are empty or garbled

The endpoint probably isn't speaking standard /v1/chat/completions streaming. Try a different model or provider profile.

ℹ️ Benign startup noise

Seeing [providers] fetch failed in a log at startup is normal when your local model runtime isn't up yet. Start it and Refresh — it's not a broken server.
