# Production build plan for the native Agent Browser

The release scenario is simple. From a Code chat, open the agent's tab, take control, sign in, point Guide at an element, and hand the same signed-in page back to the same agent. The agent's next eligible turn should receive the note and identify the intended element. Exercise that whole path through the packaged Electron viewer.

## What the current implementation explains

| Symptom | Evidence in the current working tree |
| --- | --- |
| Typing and scrolling feel delayed | `src/agent-browser/viewer.ts` uses a 500 ms frame interval. `captureFrame` in `server/agent-browser/index.js` captures full PNGs and skips busy tabs. Input and capture share the tab command queue. A successful input response can precede visible feedback by multiple polling intervals. Actual latency still needs measurement. |
| Keys behave differently from a browser | The viewer cancels keydown, includes printable text only with zero modifiers, and sends independent HTTP requests. The service synthesizes immediate key-up for this path. Shifted punctuation in passwords, held modifiers, selection shortcuts and rapid edits are concrete repro cases. Pointer handling in the viewer sends a click rather than a drag sequence. |
| Some sign-ins cannot complete | The isolated browser closes additional page targets, including login popups. Navigation policy also applies to identity-provider redirects. The disposable profile explains loss of session state after teardown. The provider and failing step in the reported account flow are still unknown. |
| Guide appears to do nothing | The viewer requires both a selected element and a nonblank note, but enables Send based on selection alone. Selection checks the latest capture revision even if another capture finished after the displayed frame. Tokens expire after 60 seconds. The API can report delivery when it puts a note in a runtime queue, before a runner consumes it. These are distinct failure points. |

## Delivery order

1. **Build one repeatable desktop reproduction.** Use a scratch Minnow home, deterministic model, and local two-origin fixture with a form, a popup identity provider, callback, scrollable content and a moving target. Drive the actual viewer from Code. Record input enqueue, browser dispatch, resulting page change, and viewer paint with correlation IDs. Record Guide selection, queue and consumption with owner/run IDs. Exclude typed values, clipboard data, cookies and callback query strings. Establish p50/p95 on a named Windows machine in dev and packaged builds. Separately reproduce the user's actual provider with a test account when available.

2. **Host a live Chromium tab inside the desktop Agent Browser.** Start with the native WebContentsView pattern in electron/preview-host.ts. Create an isolated agent session at reservation time, with its own guest and controlled popups. The existing headless browser runs in a separate process. Loading its URL into Preview would drop form, session and navigation state. Give the server-owned tab and lease a desktop backend which forwards authorized automation commands to that exact guest through Electron main. Keep the existing headless driver for runs without Electron. Keep screenshots available as an explicit agent tool.

   Prototype one tab end to end. Watch displays the guest while the agent drives. Take Control drains or cancels in-flight agent work and grants native focus only once control is exclusive. Chromium handles typing, composition, clipboard, selection, drag and scroll. Guide intercepts a pick on the live page, suppresses the underlying click, highlights the element, and binds its identity to the current document and owner. Handback restores agent access on the same guest. Closing the viewer detaches the display while the run retains the tab. Verify process cleanup and isolation on release, quit and crash.

   Prove rapid typing, shifted punctuation, IME, drag selection and trackpad scrolling on packaged Windows. Test a real account provider early. If its policy requires a standalone browser, investigate the installed Chrome/Edge driver in visible mode with a dedicated agent profile. Launch the chosen backend before navigation so handoff never depends on migrating a live session.

3. **Complete sign-in under human control.** Support same-tab redirects first, then one user-initiated popup associated with its opener and isolated session. Show the destination origin and allow approval of the identity-provider hop. Preserve opener/callback behavior, close or cancel cleanly, and verify success via an authenticated action in the original tab after handback. Keep agent reads, screenshots and mutations gated during credential entry and recheck origin and lease on resume. Test denied origins, failed credentials, MFA, cancel and retry, and isolation from a second agent. Validate a real provider separately from the local fixture. Treat persistence across launches as a separate opt-in product decision.

4. **Make Guide delivery observable.** This can start alongside Take Control. Trace the default Code chat first, then test idle chat, managed chat, subagent and board owners individually. Advertise availability according to whether that owner has a consumer. Bind the live element selection to its tab, owner and document. Revalidate the target before sending. If it moved, highlight the changed target if identifiable and retain the note for reselection. Show who will receive the note before Send, disable Send until valid, and show separate states for queued, included in the owner's turn, and owner finished. Use one guide ID across submission, retries and acknowledgement. Preserve the draft on failure and offer reassignment when the owner is gone.

## Release gates

- **Take Control** — proposed local desktop targets are p95 key-to-visible-character below 100 ms, at least 20 visible updates per second during continuous scroll, and zero lost, duplicated or reordered characters in a 200-character burst. Measure with another agent tab busy. Verify hide/show, disconnect and rapid handback cannot replay input to the wrong tab.
- **Sign-in** — redirect and popup fixtures each complete ten consecutive runs through the actual viewer. The agent resumes authenticated on the original tab, while a second owner cannot access the session. Record the supported result for the reported provider before calling that incident resolved.
- **Guide** — assert the exact note and target in the owning model's next eligible request and check the acknowledgement shown in the viewer. Exercise idle-to-active, selection during a DOM update, navigation, reassignment, expired selection and disconnect after submit. A retry delivers once. An unsupported or finished owner gets an actionable message.
- **Regression and rollout** — run service, live Chromium, API/runtime and viewer suites. Fix the tab-switch viewer test to wait for the second image to paint before its assertion, then check whether a product race remains. Gate rollout on the packaged workflow above, verify the primary chat/tool loop remains responsive, and keep the existing backend available during the staged rollout.

## Investigation baseline

On the Windows working tree, the 11 service unit cases passed. The two live Chromium and four trusted-runtime integration cases passed, including idle foreground Guide queueing. The viewer and foreground-runtime run passed eight of nine cases. The Guide tab-switch test observed the second frame request but failed to find a painted image, then reported async activity after teardown. These results cover individual components. Desktop latency, real account sign-in and end-to-end Guide consumption from the reported session still need reproduction.

## Implementation milestones and dependencies

Each milestone ends in a working vertical slice. The backend selection decision in M1 precedes investment in viewer chrome. M4's runner delivery work can proceed after M2 establishes trusted owner and document identity.

### M1 — Decide the desktop browser host with a packaged prototype

- Reuse the mounting and bounds pattern from `electron/preview-host.ts` and the auxiliary window lifecycle in `electron/agent-browser-viewer-lifecycle.ts`. Give the guest a unique ephemeral partition, separate from Preview and Minnow's own authenticated renderer. Exercise one real agent snapshot, user edit, then agent read on the same page.
- Run the sign-in fixture and the affected provider with a test account and user-entered credentials. Record browser/version, OS, provider, flow, supported factors and the step that passed or failed. Test third-party cookie behavior, user-initiated popups, passkeys or OS prompts where the provider requires them. Document provider restrictions and use a provider-supported flow. [Google OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies)
- If the embedded host passes, proceed with it as the desktop default. If a required provider excludes embedded browsers, evaluate a visible installed browser with a fresh agent profile. It must pass the same exclusive control, popup, privacy, Guide and cleanup tests. A visible external window also needs a demonstrable means of preventing accidental input in Watch and intercepting a Guide pick. If neither host qualifies, mark that provider unsupported and hold the affected release claim. Choose the backend when reserving the tab and disclose any separate-window behavior.
- **Exit evidence:** packaged Windows recording using fixture credentials, sanitized real-provider result, baseline latency, and a written backend decision. No live account recording during credential entry.

### M2 — Implement the desktop backend behind the existing service

- Keep `server/browser-agent-api.js` and `server/agent-browser/index.js` authoritative for the workspace, owner, lease, mode, revision, origin policy, queue, capacity and timeouts. Retain the existing tool names, explicit tab IDs, screenshot return shape and stale-reference behavior. Scope native guest lookup to the authenticated service instance and tab generation.
- Inventory the operations currently reaching `tab.session` and its protocol client. Extract the smallest common session interface for navigation, snapshots, evaluation, actions, capture, events and disposal. Run identical service contract tests against a disposable Chromium session and an Electron guest. The headless CLI, scheduler, boards and tests must still work with Electron absent.
- In the packaged host, connect the service to Electron main through an injected adapter. In development, the Node server and Electron can run separately. Prove a private, per-boot authenticated local bridge with protocol versioning, capability negotiation, cancellation, bounded requests and sender validation. Only trusted Minnow chrome may request viewer attachment or mode changes. Never expose raw debugging commands, a general IPC proxy or the session token to web content. Select the backend once per reservation, fail visibly if its host disappears, and reject stale responses after reconnect.
- Mount only the active guest in the viewer's content bounds. Test resize, display scaling, zoom, fullscreen, tab switching, focus return, keyboard-only navigation, screen-reader mode announcements and native menus/dialogs over the guest. Watch must block pointer, wheel, keyboard and focus-driven page activation while keeping viewer controls accessible. The native path should issue zero periodic frame requests.
- **Exit evidence:** reserve, navigate, snapshot, click, fill, screenshot and release through a normal Code chat in dev and packaged builds. Opening and closing the viewer preserves the live page. Running the contract under plain Node produces the same tool-level outcomes.

### M3 — Ship exclusive handoff and private sign-in

| Event | Required behavior |
|---|---|
| User requests control | Move to transferring, increment the revision, reject queued work from the previous revision and drain active work with a deadline. Grant guest focus only after the server confirms exclusivity. An uncertain command completion quarantines the tab. |
| User types credentials | Gate every agent read and mutation, including eval, screenshots, snapshots and background observers. Suppress developer diagnostics that capture content. Only the focused native page receives keystrokes. |
| Identity provider opens a window | Validate the opener, user gesture, destination and navigation grant. Bind the child to the same isolated session and control lease. Deny unsolicited windows, external protocols and privileged URLs. Keep the trusted origin and active popup visible in Minnow chrome. |
| User returns control | Close or resolve the auth child, check the current origin and owner, invalidate pre-login element references and acquire fresh state. Enable agent work only after explicit handback. The user can cancel and discard the session instead. |
| Viewer closes during control or Guide | Detach the view, retain the paused ownership state and allow reopening or explicit disposal. Closing the window must never silently grant an agent access during sign-in. |
| Tab released or reassigned | Default cross-owner assignment to fresh storage. For a live authenticated handoff, require an explicit user choice identifying the destination owner and the signed-in origin. Treat every used session as potentially authenticated. Clear child windows, grants and handles on disposal. |

Use sandboxed guests with context isolation and Node disabled. Apply explicit permission, download and navigation policies to every guest and child. Check listener provenance so a paired phone or another renderer cannot invoke desktop-only operator actions. Exercise attempts from a hostile fixture to access preload APIs, local files, host endpoints and another owner's guest. A fresh session isolates storage but does not erase scripts the agent previously ran in the page. Threat-model preinstalled event listeners and credential capture before promising private sign-in. If the existing page cannot be trusted, require a clean, user-started login context with automation suspended before loading the login page, then grant the resulting session to the selected owner. [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security)

**Exit evidence:** cover every transition with a delayed command, stale lease or disappearing window. Inspect the agent transcript, tool responses and diagnostic output using synthetic credential canaries. Verify a successful authenticated operation after handback, plus denied origin, denied transfer, cancelled login and a second concurrent owner.

### M4 — Deliver Guide from the live page into the owning turn

- Use browser inspection/hit testing in the native host. Freeze agent mutations during selection. Consume the selection gesture before page activation, provide a visible highlight, and support Escape to cancel plus a keyboard-accessible picker. Test scaled displays, scrolling, nested frames, shadow DOM and replacement of a selected node. For an uninspectable target, explain the limitation and allow the user to choose a reachable element.
- Keep the trusted element identifier bound to the tab, document generation and owner. Derive summaries from safe labels and roles. Omit field values and credential-bearing URLs. Treat page labels as untrusted text in the model context. Return the draft for reselection when the document, target or owner changes.
- Trace `src/tools/agent-browser-runtime.ts`, the foreground chat round boundary, the managed Code chat path, and the board/subagent effectors individually. Register a consumer at each supported owner boundary. Use stable owner IDs for routing and display names for presentation. Show unavailable before composing for a recipient without a consumer.
- Generate the guide ID before the first submit. Retried requests with that ID return the original outcome. For supported idle chats, persist the pending note in workspace-scoped chat storage, with expiry and bounded retention. Deduplicate by guide ID at transcript insertion. Acknowledge only after the owning turn incorporates the row. On restart, distinguish a pending text note from a live target whose session ended. Never reuse a dead element handle. Reuse chat persistence and backup rules when adding storage.
- **Exit evidence:** run the picker through the real viewer and inspect the next model request. Assert one note for the intended owner and zero for a concurrent owner across timeout, duplicate submit, restart, cancellation and reassignment. Check that the underlying form's submit counter stays zero.

### M5 — Recovery, operations and qualification

- Use the existing service tab cap and watchdog. Bound popup count, pending Guide entries, protocol commands and guest shutdown time. On renderer crash, debugger detach, Electron quit or bridge loss, revoke affected leases, close descendants and release resources. Offer a fresh tab after loss. Never retry a click, submit or navigation automatically when its result is unknown.
- Add local diagnostics for backend/version, handoff duration, failure category, queue depth, Guide acknowledgement delay, guest count and cleanup outcome. Redact URLs to origins and omit content, screenshots, note text and identifiers useful for recovering a session. Provide a troubleshooting route for blocked origin, unsupported provider, lost guest and missing Guide consumer.
- Run service/API/runner and viewer suites in CI plus Electron tests for native input and focus. Use a deterministic two-origin fixture for unattended CI. Reserve actual provider checks for controlled release qualification. Run the primary flow on packaged Windows, macOS and Linux before enabling each platform, including keyboard layouts, platform clipboard shortcuts, IME, native auth dialogs and multiple monitors where supported.
- Run a 60-minute soak with repeated opening, takeover, Guide, handback and closing. Fill all eight reservations, close them, and repeat. Assert zero surviving guests, children, leases or listeners after disposal and no monotonic memory growth across warmed cycles. Compare Code chat responsiveness and hidden-viewer CPU against the M1 baseline. Record failures and hardware beside the performance targets above.
- **Exit evidence:** attach the platform/host results, latency distribution, soak report, negative security tests and sanitized failure examples to the release checklist. A passing mock or a request being sent is insufficient evidence of painted output, authenticated handback or model consumption.

### M6 — Rollout, rollback and documentation

1. Ship behind a desktop capability flag, initially off. Enable for internal packaged runs, then opt-in users, then by qualified platform. The chosen backend remains fixed for each active reservation.
2. Block promotion on credential leakage, cross-owner access, duplicated side effects, stuck takeover, a failing required provider or a Guide acknowledgement without model consumption. On regression, switch new reservations to the previous backend. Let existing healthy sessions finish or offer explicit closure. Quarantine unsafe sessions immediately.
3. Update the shipped manual, browser skill and tool prompts with supported sign-in behavior, session lifetime, Guide receipts and recovery steps. Update `documentation/context.md` with the backend boundary, local bridge and storage details when shipped. Include relevant backup catalog coverage if a new top-level persistent store is introduced.
4. Remove the desktop screenshot/input emulation path only after native qualification and a successful rollback rehearsal. Retain explicit screenshot tools and headless coverage for unattended runs.

**Definition of done:** the packaged release passes the end-to-end scenario, security and recovery cases, and release gates on every enabled platform. The user can tell who controls the page, which account session they are handing back, and whether the intended agent actually received their guidance.
