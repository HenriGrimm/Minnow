# MIN-344 — Fix scrolling in composer input when text overflows

**Date:** 2026-09-12
**Goal:** Make the Code composer input scrollable (wheel/trackpad and caret-driven) once its content exceeds the 40vh cap, on both the CSS `field-sizing` path and the JS fallback path.
**Granularity:** medium

## Context

Issue MIN-344 (bug, urgent): the composer input field does not allow scrolling when the amount of text exceeds the visible display area. Expected: users can scroll within the composer to view and edit content beyond the visible bounds.

Verified current state (this repo):

- The Code composer is `<textarea id="msgInput">` (`index.html:2519`), styled in `src/styles/input.css` (`#msgInput`): `min-height: 44px`, `max-height: 40vh`, `field-sizing: content`, `overflow-y: auto`, `scrollbar-width: none` (+ hidden `::-webkit-scrollbar`).
- `src/ui/composer-auto-resize.ts` — `autoResize(el)` / `bindComposerAutoResize(el)`:
  - When `CSS.supports('field-sizing', 'content')` is true (`composerFieldSizingSupported()`), the function only clears leftover inline height; CSS does the rest. This path is already scrollable (CSS `overflow-y: auto` + `max-height` cap) — **no change needed beyond CSS task W1-B**.
  - JS fallback path (field-sizing unsupported): the capped branch sets `el.style.overflowY = el.scrollHeight > maxPx ? 'auto' : 'hidden'`. Because `maxPx` is the **CSS max-height** (40vh of window), a box already sitting at max height with overflowing content has `scrollHeight <= maxPx` and gets `overflow-y: hidden` — the textarea is capped, content overflows, and it **cannot scroll** (wheel does nothing, and the caret cannot move past the visible area). The same `hidden` default also applies in the shrink/fit branches.
  - The skill-chip overlay (`src/ui/composer-skill-highlight.ts` + `src/styles/skill-chip.css`) wraps the textarea in a `.composer-skill-highlight-host` flex host with an absolute `inset: 0; overflow: hidden` layer that mirrors `scrollTop` — it is paint-only and does not block textarea scrolling, but tests must keep it in mind (the host is created on first sync).
- `src/ui/chat-scroll.ts` binds wheel/scroll handlers only to transcript roots (`#chatArea`, `#chatAppArea`, board panes) — it does not intercept composer wheel events. No other wheel interception touches `#msgInput` (verified by search).
- Existing tests: `test/ui/composer-auto-resize.test.mjs` (happy-dom; asserts `overflowY: 'hidden'` for short content and height caps). `npm test` runs the full suite via `node test/run-all.mjs`.
- History: `documentation/archive/composer-macos-input-lag.md` — field-sizing + JS fallback was introduced to fix macOS typing lag; the fallback's `height: auto` skip is intentional and must be preserved.

Constraint: do not reintroduce per-keystroke `height: auto` reflow on the fallback path (macOS lag regression), and do not change the 44px/40vh caps.

## Wave Breakdown

### Wave 1 — Fix

#### Task W1-A: Key composer auto-resize overflow-y off real overflow
- **Build:**
  - In `src/ui/composer-auto-resize.ts`:
    1. Add a private helper `applyComposerOverflowY(el: HTMLTextAreaElement): void` that sets `el.style.overflowY = el.scrollHeight > el.clientHeight + 1 ? 'auto' : 'hidden'` (same +1px tolerance used elsewhere in the file).
    2. In `autoResize()`, replace every direct `el.style.overflowY = …` write with a call to `applyComposerOverflowY(el)` **after** the height for that branch has been set:
       - Capped branch (currently `el.style.overflowY = el.scrollHeight > maxPx ? 'auto' : 'hidden'`): set height to `next`, then call the helper. A box at max height with overflowing content now gets `overflow-y: auto` instead of `hidden`.
       - Shrink-to-min branch (`current <= minPx + 1`): after setting `height` to min, call the helper (empty/short content → `hidden`, as today).
       - Fit branch (`contentHeight <= maxPx`): after setting the fitted height, call the helper (no overflow → `hidden`, as today).
       - Final cap branch (`contentHeight > maxPx`): after setting `height` to `maxPx`, call the helper (overflow → `auto`).
    3. Do **not** change the field-sizing path (`clearInlineComposerHeight` + `syncSkillHighlight` early return), the `height: auto` skip on single-line typing, or `composerMinHeightPx` / `composerMaxHeightPx` / `composerFieldSizingSupported` / `bindComposerAutoResize` signatures.
  - In `test/ui/composer-auto-resize.test.mjs` (happy-dom, same setup as existing cases):
    1. Add a test: with field-sizing forced off (`setComposerFieldSizingSupportedForTests(false)`) and a tall `minHeight` on the element to simulate a capped box (e.g. `el.style.minHeight = '300px'`), set a value whose `scrollHeight` exceeds the client box, run `autoResize(el)`, and assert `el.style.overflowY === 'auto'` and that `el.style.height` does not exceed the 40vh cap (320px for the 800px test window).
    2. Add a test: after an overflow state (from the previous scenario), shrink the value to one line, run `autoResize(el)`, and assert `el.style.overflowY === 'hidden'`.
    3. Keep all existing assertions green — in particular `short content stays hidden overflow under 40vh cap` and `cleared value resets to minimum height` must still pass unchanged.
  - Expected diff scope: ~15–30 lines in `composer-auto-resize.ts` (helper + 4 call sites), ~40–70 lines of new tests.
- **Test:** `npm test` (full suite via `node test/run-all.mjs`) passes, including `test/ui/composer-auto-resize.test.mjs`. If the suite runner needs a suite filter, run `node --test --test-force-exit test/ui/composer-auto-resize.test.mjs` directly to check the file in isolation first.
- **Accept:** With the JS fallback active, a capped composer textarea whose content overflows its box has `overflow-y: auto` (wheel/trackpad scrolls it and the caret moves into view), while short content keeps `overflow-y: hidden` and the existing no-`height:auto` typing behavior is unchanged.
- **Touches:** `src/ui/composer-auto-resize.ts`, `test/ui/composer-auto-resize.test.mjs`

#### Task W1-B: Composer CSS — contain scroll chaining on #msgInput
- **Build:**
  - In `src/styles/input.css`, inside the existing `#msgInput { … }` rule (around line 320–342): add `overscroll-behavior: contain;` next to `overflow-y: auto;`. This stops wheel/trackpad scroll chaining from the capped composer into the chat transcript when the user scrolls past the composer's top/bottom edge.
  - Do **not** change `max-height: 40vh`, `min-height: 44px`, `field-sizing: content`, `scrollbar-width: none`, or the hidden `::-webkit-scrollbar` (hidden scrollbars are the established look; wheel + caret scrolling are the interaction).
  - Expected diff scope: 1 line.
- **Test:** `npm run build` passes (Vite CSS scan is fine — no new class names). Manual check via `npm start`: type/paste >40vh of text into the Code composer, wheel up/down inside the field scrolls the field; holding the wheel at the field's top edge does not scroll the chat transcript behind it.
- **Accept:** With overflowing composer content, scrolling at the composer's edges stays contained in the textarea (no transcript scroll chaining), and the field itself scrolls via wheel/trackpad.
- **Touches:** `src/styles/input.css`

## Notes for Build Agents
- The macOS typing-lag fix is load-bearing: never add `height: auto` back to the hot path of `autoResize`, and never touch the field-sizing early return.
- `autoResize` is also bound to other composer textareas via `initComposerInput` (`src/ui/input.ts`) — the overflow fix is generic to any bound textarea; do not special-case `#msgInput` by id.
- happy-dom does not do real layout; existing tests assert on inline `style.height` / `style.overflowY` strings, so new tests should assert on those same properties (and on the 320px cap for the 800px test window), not on rendered pixels.
- The skill-highlight host (`composer-skill-highlight.ts`) wraps the textarea lazily on first sync; it must not be modified in this plan.
- Windows repo, CRLF files — use the normal edit tools; line endings are auto-matched.
