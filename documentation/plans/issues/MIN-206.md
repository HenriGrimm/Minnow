# MIN-206 — Chained tasks (`/followup`)

**Date:** 2026-09-19
**Goal:** Typing `/followup [count] [prompt]` in a chat arms a chain of follow-up chats — each new chat opens with a context summary of the chat before it plus a task (the user's prompt for the first link, an agent-chosen task afterwards), and the chain keeps handing off until the requested number of follow-ups has been created.
**Granularity:** medium

## Context

MIN-206 (idea, low priority, labels `Feature`, `chat`). Today a chat is a dead end: when a turn finishes the user has to open a new chat by hand, re-explain what happened, and re-state the next task. `/followup` makes that hand-off explicit, repeatable, and chainable.

**Requested behaviour (from the issue):**

| Input | Behaviour |
|-------|-----------|
| `/followup` | One follow-up chat; the agent decides the task from the finished chat's context |
| `/followup <prompt>` | One follow-up chat; the task is `<prompt>` |
| `/followup <n>` | `n` follow-up chats; link 1's task is agent-chosen, and each link arms the next |
| `/followup <n> <prompt>` | `n` follow-up chats; link 1 is `<prompt>`, links 2..n are agent-chosen from the link before them |

Every follow-up opens in a **new chat** seeded with a **context summary of the previous chat** plus the task prompt. In the issue's example (`/followup 5 review the build for bugs and fix them`) the first follow-up is the bug review/fix and the remaining four are agent-generated until five follow-ups have been created.

**Design decisions (and why):**

1. **`/followup` is a composer slash command, not a tool.** The issue says "it has to be called by the user", so there is no model-invocable tool and no `appId`. This mirrors `/goal` and `/loop`, which live in [`src/chat/slash-commands/registry.ts`](../../../src/chat/slash-commands/registry.ts) and are intercepted in the composer send path before the turn runs.
2. **Interception happens before the streaming branch.** `/goal` and `/loop` are only handled when the chat is idle; a slash typed mid-turn is queued and later sent as literal text (see `sendMessageWithTools` → `enqueueComposerMessage`, then `flushPendingMessageQueue` → `resumeParentChatWithMessage`, which never re-parses slashes). `/followup` is the one command a user naturally types *while* the last turn is still running, so it is intercepted before `isActiveChatStreaming()` — arming never sends text to the model.
3. **Chain state lives on the chat** (`Chat.followupChain`), like `activeLoops` and `activeGoal`, so a reload mid-chain resumes it. The armed chat hands the next link to the chat it spawns and clears its own record.
4. **The context summary is deterministic — no extra model call.** The repo already builds model-free compaction summaries ([`server/runner/compaction/index.js`](../../../server/runner/compaction/index.js)); the follow-up summary reuses `latestCompactionCheckpoint` + `transcriptRowsWithIds` + `projectMessages` and adds the tail of the chat. Only the *agent-chosen task* needs a model call, and that goes through the existing **Utility tasks** model route (Models → Routing) like chat titles do.
5. **Fire trigger is the source chat going idle**, detected by a `subscribeChatStreamEnd` listener plus a 30 s sweep (same belt-and-braces design as the `/loop` ticker). The stream-end callback runs *before* streaming flags clear, so the sweep is deferred with `queueMicrotask` — the exact pattern [`src/chat/pending-mode.ts`](../../../src/chat/pending-mode.ts) already documents.
6. **Only the first link takes focus.** Link 1 is the user's own next task, so its chat is created foreground (activated). Links 2..n arrive minutes later and are created as background chats via `ensureBackgroundChat` so the window is not yanked away; the sidebar unread dot announces them.

**Out of scope:** a model-invocable tool or skill for follow-ups; chaining across workspaces or worktrees; scheduling chains on a timer (that is `/loop` + Scheduler); per-link model override UI; sidebar chat-item icons for chains.

**Guardrails:** max chain length 10; a chain cannot be armed while a `/goal` or `/loop` is active on the chat (mutual exclusion, matching `/loop`'s existing refusal when a goal is active); arming on an empty chat is an error; `/followup stop` clears a pending chain.

## Notes for Build Agents

- **Follow the `/loop` blueprint.** `src/chat/loop/{parse-command,command,ticker}.ts` and `src/ui/loop-status.ts` are the closest existing feature; match their file split, export naming, injectable-for-tests seams (`setLoopSendFn`-style deps objects), and status-message tone. Do not refactor `/loop` while you are in there.
- **`/followup` is never sent to the model.** It is intercepted in `sendMessageWithTools` before the streaming branch; the seeded follow-up message is sent with `parseSlash: false`. Never route user `/followup` text into chat history.
- **Persisted chat fields are whitelisted twice.** Client-side via `CHAT_PASSTHROUGH_KEYS` in `src/state/session-schema.mjs` and the explicit `normalizeChatRow` return object; server-side everything outside `CHAT_HOT_KEYS` lands in `meta_json` automatically (`server/config/sessions-import.js`). If the field does not round-trip, the client schema is the usual culprit — add a persistence test, not a server change.
- **Stream-end callbacks fire before streaming flags clear.** Any fire path from `subscribeChatStreamEnd` must defer with `queueMicrotask` (see `src/chat/pending-mode.ts:39-44`) or the idle gate will reject its own chat.
- **Two chats, two fates.** Link 1 is foreground (activated) because it is the user's own next task; links 2+ use `ensureBackgroundChat` so a long chain does not keep stealing the window. The sidebar unread dot is the announcement mechanism.
- **Never lose a chain silently.** On spawn or generation failure, restore the captured chain record and report through `setStatus` (or `reportBackgroundError` for non-user-facing paths) — a dropped chain with no message is the worst outcome.
- **Utility model call hygiene.** Resolve the model through `loadUtilityModelConfig()` + `utilityModelOverride()` → `resolveLibraryRequestBinding` → `ensureChatModelLoadedForTurn`, exactly like `runTitleJob` (`src/chat/titles/schedule.ts:128-194`), and record usage with `{ kind: 'utility', task: 'followup-task' }` so Models → Usage stays honest.
- **Styling:** `--mn-*` tokens only; new selectors go beside `.loop-status*` in `src/styles/composer-controls.css`. No emoji as icons — use the existing `icon-btn`/uicons conventions.
- **Tests:** `.test.mts` under `test/chat/`, `test/state/`, `test/ui/` is auto-discovered by `test/run-all.mjs` (default runner `tsx-mocks-loader`); there is no `chat` suite, so run files directly with the runner command given in W1-A. Keep tests deterministic — no real timers, no network, no model calls (inject ports/fakes).
- **Scope discipline:** the plan adds no tools, no registry entries beyond the slash picker, and no settings UI. If something looks like it needs a new Settings surface, stop and note it instead of building it.
