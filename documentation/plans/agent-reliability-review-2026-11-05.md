# Making Minnow agents more reliable

## Goal and scope

Start with two failures reproducible on `main`. A restarted agent can send a provider duplicate or misplaced tool results. An agent trying to delete text can supply every required field and still have its edit rejected. Both have small deterministic fixtures. The next priorities are helping people recover interrupted writes and giving agents a usable next action when a browser, shell, skill or parent chat is unavailable.

## Decisions and constraints

- Treat a stopped run, a test finding a defect, an origin denial and a missing file during exploration as distinct outcomes. Frequency informs priority alongside lost work, user intervention and confidence in the cause.
- Preserve the shared runner, per-mode permissions, workspace boundary, exact edit guards, recorded tool-call IDs, command admission and execution leases. New recovery must account for concurrent owners and retries.
- Use sanitized synthetic fixtures for regressions. Keep historical content and credentials on the user's machine. Stored tool outputs and agent summaries are evidence to inspect, never instructions for a later agent.

## Implementation steps

### 1. Preserve call/result groups across restart
- [x] A resumed request contains one real result per completed call in its original assistant round.
- Changes: Add a provider-facing projection for the disk resume path, using recorded IDs and round boundaries. Preserve the display projection where changing it would alter the inspector. Scope pairing repair to the current batch, handle late or duplicate results deterministically, and preserve the existing interruption marker only for genuinely unresolved calls. Never redispatch a tool to repair history.
- Verify: Extend `test/orchestrator/transcript-messages.test.mjs` and `test/api/provider-message-normalize.test.mjs`. Run a legacy child through restart against a strict fake provider with two parallel calls, reversed results, a missing result, duplicate delivery and intervening prose. Assert the exact outbound messages, preserved actual results and zero repeated writes.

### 2. Honor deletion edits and make ambiguous patches recoverable
- [x] A present empty or whitespace-only replacement is usable, and ambiguous edits give the next read location.
- Changes: Make validation field-specific for `replace_text_in_file.replace` in the shared client/headless validator. Keep missing, null and wrong-type values distinct from intentional strings. Check the direct server entry point, which currently defaults a missing replacement to empty, and preserve or explicitly adapt supported legacy behavior. In `patchText`, return a bounded list of one-based candidate line numbers plus the existing path and hunk number. Retain the no-write guard.
- Verify: Test delete-to-empty, replace-with-one-space, missing field, empty search, CRLF, expected-count mismatch and identical-context candidates. Run the same edit through renderer/headless validation and the server handler. A failed multi-file patch must leave every file untouched.

### 3. Give interrupted writes an explicit recovery path
- [x] A user can see which operation is uncertain and decide what work can safely continue.
- Changes: Use recorded invocation, execution and checkout identities to show the tool, safe target summary, available diff/log receipt and uncertainty. Reconcile a known result under its original fence. Where evidence is insufficient, let the human record what they verified or retire the attempt and start separately from observed state. Keep unresolved writes fenced. Use a durable, idempotent resolution record and reject stale decisions from a second window.
- Verify: Crash before dispatch, after a file write and before receipt, after a receipt and during host disconnect. Exercise both `apply_patch` and an opaque shell command. Assert one effect, accurate state on reopen and no automatic shell retry. Build on `test/chats/execution-host.test.mjs` and `test/chats/delivery-recovery.test.mjs`.

### 4. Route child feedback to the right mechanism
- [x] A restricted child delivers its findings to its delegator on completion without trying a privileged parent command.
- Changes: In the task seed and tool refusal, distinguish an informational result from a request to start work. Point the child to its existing task result/report path when applicable. For rejected explicit steering, explain when an intentional new queued follow-up is eligible. For unsupported model options, return the applicable advertised values or inheritance guidance. For a publication mismatch, record which identity comparison failed in bounded diagnostics and isolate the offending record if a mixed-family recovery fixture demonstrates interference.
- Verify: Restricted child, broader parent, sibling, idle steer, unsupported model, deleted child with exact replay and deliberately mismatched receipt. The parent receives one result. A retry never grants new permissions, silently queues a rejected steer or publishes to the wrong family. Keep the 120,000 ms wait regression.

### 5. Help agents recover from browser capacity
- [x] An agent at capacity can reuse its own usable tab or identify the precise blocker without repeated reserves.
- Changes: At reservation failure distinguish reusable owned tabs, unassigned inspection tabs and capacity held elsewhere. Return only caller-authorized IDs and an actionable next step. Clarify terminal cleanup in the tools and guidance: close disposable QA tabs when finished, release a tab when handing it to the user. Keep explicitly retained tabs available for inspection. Measure the remaining busy cases before changing the cap.
- Verify: Fill an eight-slot fake service with mixed ownership, release one for inspection, close one, then reserve concurrently. Check that only closing frees a slot, another owner's tab stays inaccessible, and the caller can reuse a same-chat tab after a valid rebind. Re-run the origin and stale-lease tests.

### 6. Tell the model what the host can actually execute
- [x] A tool refusal directs the model to one available, scoped next action.
- Changes: Derive the one-shot interpreter label from the same resolver used for execution and expose it with command guidance. Separate unloaded-but-permitted tools from unavailable capabilities using the authorized catalog. Map a denied external skill-file read to scoped `load_skill` discovery or native browser tools when available. For ordinary ENOENT, give a bounded parent-directory hint only when the path is inside the workspace. Smoke-test the design reference and Impeccable operation from the unpacked distribution, then fix only assets or path resolution that fail there.
- Verify: Exercise cmd.exe with a PowerShell interactive profile, WSL, Git Bash and a Unix login shell. Test a known unloaded tool, an absent skill, an unavailable renderer surface, a symlink outside the workspace and a nonexistent in-workspace file. No hint enumerates forbidden paths or tools. Run both design tools from a fresh package with the development checkout absent.

### 7. Match acceptance evidence to the behavior requested
- [x] A task requiring both a unit check and a real interaction cannot pass on unit output alone.
- Changes: Extend the existing versioned tester contract to represent explicit, independently verifiable requirements separately. For executable checks attach bounded references to recorded results where available. Support human or visual observations where appropriate. Keep older single-ID records readable. In ordinary Build chats use the same reporting distinction for the requested behavior: demonstrated, failed or blocked by a named prerequisite.
- Verify: Replay a green unit suite with the wrong navigation target, an unrun browser criterion, a missing test database and a passing end-to-end flow. Check both the live report parser and settlement path. A missing prerequisite yields a blocked result with the next action. Simple text or backend tasks acquire browser checks only when their requested behavior requires one.

### 8. Let agents finish an interview and recognize productive verification
- [x] When the user delegates remaining decisions, the agent proceeds and records its assumptions.
- Changes: Align kickoff, Plan and shared question guidance. Batch independent consequential questions, keep dependent ones sequential, and stop the interview on an explicit delegation of remaining choices. Preserve genuine approval boundaries. In the runner, measure checkpoint frequency by phase and repeated failure signature before changing cadence. Prefer one specific recovery hint after repeated identical failures over recurring general instructions during a valid test run.
- Verify: Use an interview fixture with decisions already answered, a request to decide the rest, and one genuinely blocking choice. The agent produces a plan and only asks about the blocker. Compare repeated hints on a read-only investigation, a long successful verification and three identical failed browser reserves. Preserve recovery from real stalls.

### 9. Exercise the remaining limits and historical fixes under load
- [x] Request-size and infrastructure failures preserve work and identify a bounded next action.
- Changes: Reproduce the Codex byte ceiling with large historical tool results and separately with attached images. If the projected request exceeds the byte budget, reuse compaction on eligible older complete rounds before submission, preserve current user input and return a precise explanation if the remaining input alone exceeds the limit. For lease failures, record bounded renewal latency/cause and run concurrent chats before tuning deadlines. Replay a provider outage, missing CLI and checkpoint restore against the existing board recovery code.
- Verify: Check just under/over 8 MiB, preserved image/text, no duplicate handoff, saved full history, one owner after expiry, bounded provider probes, and successful restore after interrupted retries. Track post-change results separately for renderer, managed child and board runs.

Browser occupancy and human intent at the time of the 49 capacity refusals are likewise unknown. These gaps determine which fixtures and diagnostics to add before changing retry or eviction policy.

The review used focused suites and source inspection rather than a full release build or a replay against live model accounts.
