## Building the publishable draft

The beta installers contain their beta version and cannot simply be renamed or attached as 0.2.0. Rebuild using `.github/workflows/version-release.yml`, version `0.2.0`, **publish=false**. It sets package and lockfile versions in each build checkout, packages all three platforms, checks the installed agent-runtime boundary, validates feeds and installer SHA-512 values, then creates a draft and uploads assets. The source package version is intentionally unchanged here because the existing release workflow owns the packaged version.

Before dispatch, commit and push the release notes/readiness files to the intended source branch. Pin and record that pushed commit; it should differ from the successful nightly only by the documented design exports and release documentation. A moving main branch must be rechecked before dispatch. The workflow resolves the dispatched revision to a SHA for its builds. If main has advanced with runtime changes, use a branch pinned to the reviewed source plus the release documentation instead.

```sh
gh workflow run version-release.yml --ref <reviewed-pushed-branch> -f version=0.2.0 -f publish=false
```

Then wait for the workflow, inspect the draft target/tag/assets, and perform packaged smoke checks on Windows, Linux and macOS. Check upgrade from stable 0.1.13 and the approved nightly, model connection, ordinary and delegated chat, approval/deny, issue review/delivery, phone connection/revocation, and update feeds. Stable 0.2.0 should sort above 0.1.14-beta; confirm actual updater behavior rather than relying only on version ordering. Current CI failures and the migration/native certification limits must remain visible to the release owner.

Only after acceptance publish the draft as Latest. Publishing is deliberately not part of this preparation. No draft has been built or published by this preparation step; stable installer checks and interactive smoke checks remain pending.
