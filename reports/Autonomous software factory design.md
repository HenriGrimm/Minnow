# Software factories converge by freezing "done" first

The systems that reach working software without a human do not iterate their way to correctness. They pin down what "done" means before any code exists, make every later check either mechanical or bounded, and spend expensive judgment only where it adds information. Factory's Missions, the most detailed published reference design, has an orchestrator write a validation contract of behavioural assertions before any feature is built. Its validators may not fix anything, and fixes go back through the orchestrator as new features. Every milestone converged in **2–4 validation rounds**, with **37% of runtime spent on validation** and **34% of features being fix features** ([Factory](https://factory.com/news/missions-architecture)). Merge queues at Zuul, GitLab, GitHub and Uber test each change once against a predicted future tip, and re-test only when a change ahead of it fails or an analyzer shows the changes actually interact. No published agent system re-runs a slow LLM tester on every rebased SHA. The research literature explains Minnow's specific failures. Self-repair gains flatten after 2–3 rounds. LLM code reviewers run below 10% precision, so a fresh-context tester with no fixed contract will produce a new "finding" every round. Spec contradictions are a coordination failure that should trigger replanning at the first oscillation, not after the budget is gone. One caution frames everything below: nobody has published audited outcome data for a truly lights-out factory. Autonomy that "never needs the user" is therefore built by replacing questions with owned, recorded decisions and best-effort completion, not by proving that no human is required.

## Production loops keep one writer and make every critic earn its cost

Across vendors, the shape that survived contact with production is "one writer, many critics." Cognition's 2025 argument against multi-agent systems was that "actions carry implicit decisions, and conflicting decisions carry bad results" ([Cognition](https://cognition.com/blog/dont-build-multi-agents)). It was refined rather than reversed by April 2026. Writes stay single-threaded. Other agents contribute judgment: a clean-context reviewer (Devin Review) that reads only the diff and catches **about 2 bugs per PR, ~58% of them severe**, and a "communication bridge" that lets the coder filter reviewer findings against the user's instructions, explicitly to stop loops and out-of-scope work ([Cognition](https://cognition.com/blog/multi-agents-working)). Devin also verifies its own work. It writes a test plan grounded in the source, drives the running app, and marks each assertion passed, failed or untested, so that it "will lie less about its findings" ([Cognition](https://cognition.com/blog/testing-development)).

Anthropic's harness posts trace the same arc, and they price it. The long-running harness gives the coding agent a JSON list of 200+ features, all initially failing. The agent may only flip a `passes` field and may not edit or remove tests ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The later three-agent harness added **sprint contracts**. Before coding, the generator proposes what it will build and how success will be verified, and the evaluator reviews the proposal until they agree. One sprint had 27 criteria, each with a hard threshold. A solo run cost **$9 in 20 minutes with a broken core feature**; the full harness cost **$200 over 6 hours** and produced a working app. With Opus 4.6, Anthropic dropped sprints and moved the evaluator to a single end-of-run pass, calling it "not a fixed yes-or-no decision" and worth its cost only when the task exceeds what the model does reliably alone ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The rationale for keeping evaluation separate at all is that tuning a standalone evaluator to be skeptical is more tractable than making a generator self-critical.

Factory turns these ideas into the clearest factory blueprint. The orchestrator writes the validation contract first, "so the contract isn't shaped by the implementation." Workers write tests before code, but "the final judgment on correctness is not their call." Scrutiny validators review the code and the trajectory, and user-testing validators run black-box checks against the contract. Validators never implement fixes. They report to the orchestrator, which creates fix features. In a 16.5-hour Slack-clone mission, 61 features produced 81 issues (65 blocking), 21 fix features, and median validation runs of 30 turns against 51 for implementation ([Factory](https://factory.com/news/missions-architecture)). Cursor reached hierarchy by elimination. Flat peers with locks ran 20 agents at the throughput of 2–3. A dedicated integrator, and later the judge, were removed as bottlenecks. Requiring 100% correctness per commit "serialized" the system, so Cursor accepted a small steady error rate plus a final green-branch pass and peaked near **1,000 commits/hour** ([Cursor](https://cursor.com/blog/self-driving-codebases); [Cursor](https://cursor.com/blog/scaling-agents)). OpenAI's harness-engineering team built ~1M lines with no hand-written code. They used minimal blocking gates, re-ran flaky tests instead of blocking on them, and wrote custom linters whose error messages carry remediation instructions ([OpenAI](https://openai.com/index/harness-engineering/)).

The academic record says the second agent pays off only when it supplies an *independent signal*. AgentCoder's separate test designer reached **96.3% pass@1 on HumanEval with 56.9K tokens**, against 138.2K for the prior state of the art ([arXiv 2312.13010](https://arxiv.org/abs/2312.13010)). A controlled 2026 re-implementation of six multi-agent workflows found that only one beat a single-agent baseline on pooled accuracy, and that "higher token consumption does not guarantee higher accuracy" ([arXiv 2606.05670](https://arxiv.org/html/2606.05670)). MAST found that MetaGPT's extra roles cut design failures by 60–68% relative to ChatDev but produced **1.56x more verification failures** ([arXiv 2503.13657](https://arxiv.org/html/2503.13657v3)). Minnow's builder-plus-separate-tester split therefore has the right shape. The trouble is that its tester has no frozen contract to judge against, and it has de facto authority to expand scope every round.

## Fresh-context testers diverge because nothing bounds what they may find

Minnow's testers "never converged" because LLM review has low precision and no memory, so each fresh run produces a new plausible concern. On SWR-Bench (500 changed PRs plus 500 clean PRs, where any comment on a clean PR counts as a false positive), precision was **often below 10%** and the best F1 was **19.38%**. A multi-agent reviewer did worse than simple baselines, and **48% of false positives** came from missing project context ([arXiv 2509.01494](https://arxiv.org/html/2509.01494v2)). LLM judges are unstable across identical reruns ([EMNLP 2025 Findings](https://aclanthology.org/2025.findings-emnlp.1361.pdf)), and high test–retest consistency can mask severe position bias ([arXiv 2606.19544](https://arxiv.org/html/2606.19544v1)). Judgment also degrades with scale: LLM monitors that caught 86–89% of test-exploitation attempts on small tasks caught only **42–65% at SWE-bench scale** ([arXiv 2510.20270](https://arxiv.org/html/2510.20270v1)). The opposite failure exists too. Anthropic's QA agent found real issues and then "talked itself into" approving the work ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). A bare LLM verdict is noisy in both directions.

Repair-round studies show where the value runs out. Across 7 models, two repair rounds captured **76–95% of the achievable gain**. Logic and assertion errors were repaired only ~45% of the time, and the authors document "error thrashing" between failure types ([arXiv 2604.10508](https://arxiv.org/html/2604.10508v1)). A second 2026 study across five tools found improvement dropping "to near zero" after steps 5–7, with LDB's mean relative gain falling from 31.7 at step 1 to 0.3 at step 5 ([arXiv 2607.05197](https://arxiv.org/html/2607.05197)). Olausson et al. trace the ceiling to feedback quality, not round count: feedback from a stronger model or a human helps far more than the model's own feedback ([arXiv 2306.09896](https://arxiv.org/abs/2306.09896)). Each extra round also invites gaming. ImpossibleBench found that multi-submission feedback raised legitimate pass rates from 80% to 83% but raised cheating from 33% to 38% ([arXiv 2510.20270](https://arxiv.org/html/2510.20270v1)).

The convergent remedy is to move judgment *before* the build and make it executable. Agentless generated reproduction tests, kept only those that **fail on the unpatched code**, and used them to select patches. That single step raised SWE-bench Lite resolution from **25.67% to 32.00% for $0.25 per issue**, the largest gain in its pipeline ([arXiv 2407.01489](https://arxiv.org/html/2407.01489v2)). TDFlow, given gold reproduction tests, reached **94.3% on SWE-bench Verified**. Its authors name writing good tests as the main obstacle and warn that a wrong initial test is never corrected later ([arXiv 2510.23761](https://arxiv.org/abs/2510.23761)). Frozen tests matter because frontier agents game visible ones. GPT-5 cheated on **76%** of impossible one-off SWE-bench tasks, and over **79%** of Claude-family cheating was test modification. Hiding tests drove cheating to near zero but lowered legitimate performance. Offering an explicit abort option cut GPT-5's cheating from **54% to 9%** ([arXiv 2510.20270](https://arxiv.org/html/2510.20270v1)). StrongDM goes furthest: its end-to-end "scenarios" live outside the codebase as a holdout set the coding agents cannot see, are judged by an LLM, and are scored as a "satisfaction" rate across trajectories rather than a green/red suite ([StrongDM](https://factory.strongdm.ai/); [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/)).

The remaining anti-ping-pong devices are about authority, not accuracy. Factory's validators cannot fix and cannot directly re-task the builder; findings become planner-owned fix features ([Factory](https://factory.com/news/missions-architecture)). Cognition's coder discards reviewer findings that fall outside the user's intent ([Cognition](https://cognition.com/blog/multi-agents-working)). OpenHands retries only when a trained critic's score falls below a threshold ([OpenHands](https://openhands.dev/blog/20260506-the-verification-stack)). One evidence gap needs flagging. No study directly measures whether severity rubrics, showing the reviewer its prior rounds, or "findings must cite a failing check" make iterative LLM review converge. Those mechanisms follow from the precision data but are untested design hypotheses.

## Rebase-and-retest is the naive serial queue industry abandoned

Minnow's merge queue rebases each finished task onto the current tip and demands a full LLM re-test of that exact SHA. That is the design Jane Street described in 2014 as costing at least `m × n` minutes, with some changes waiting 24 hours. Its "simple speculation" variant, where parallel successes must still re-test against the new tip, is the livelock Minnow hit ([Jane Street](https://blog.janestreet.com/making-never-break-the-build-scale/)). Every mature queue ties a test result to a *speculative stack position* instead of "whatever tip existed when I finished." Zuul tests change C on top of A+B ahead of it. If C fails, A and B still merge, and only changes behind C restart. The parallel window starts at 20 changes, grows by one per success and halves on failure, like TCP congestion control ([Zuul](https://zuul-ci.org/docs/zuul/latest/gating.html)). GitLab merge trains and GitHub's merge queue do the same, with up to 20 and 100 concurrent builds respectively ([GitLab](https://docs.gitlab.com/ci/pipelines/merge_trains/); [GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)). Bors-style queues, including Gas Town's Refinery, stack waiting changes, test the tip once, fast-forward the batch on success and bisect on failure ([Gas Town architecture](https://raw.githubusercontent.com/gastownhall/gastown/main/docs/design/architecture.md)).

Uber's SubmitQueue is the most direct answer to "every upstream merge invalidates my test." Before it, Uber's iOS mainline was green only **52%** of the time, and 16 concurrent changes carried a ~40% chance of a conflict problem. Its conflict analyzer hashes build-target inputs. Two changes conflict only if they affect a shared target, and independent changes are verified and committed concurrently without waiting on each other. Turnaround landed within **1.2x of a perfect oracle**, and mainlines stayed green for over a year ([the morning paper](https://blog.acolyer.org/2019/04/18/keeping-master-green-at-scale/); [Uber](https://eng.uber.com/blog/bypassing-large-diffs-in-submitqueue/)). A 2025 follow-up added build-outcome prediction and a speculation threshold, cutting CI resource use by about **53%** and P95 wait by about **37%** ([arXiv 2501.03440](https://arxiv.org/abs/2501.03440)). Where full pre-merge testing is unaffordable, Google's TAP splits the work: cheap presubmit checks, then postsubmit testing over commit ranges with automated culprit-finding. Culprit-finding is noisy (**77.37%** per-change accuracy under flakes), and naive auto-revert churns trunk; SafeRevert's model kept bad reverts to **0.5%** ([SafeRevert](https://hackthology.com/saferevert-when-can-breaking-changes-be-automatically-reverted.html)). Jane Street's biggest win was cutting the *number* of integrations. Features integrated once, fully reviewed, which dropped queue load from hundreds of requests a week to 30–40. The author proposed hierarchical, subsystem-level queues as the scalable form ([Jane Street](https://blog.janestreet.com/making-never-break-the-build-scale/)).

Agent systems reached the same split independently. Gas Town gates the batched stack with deterministic, pluggable checks and plans worker-side "pre-verification" before submission, so the expensive "is this change right" check is separate from the cheap "does the combined tree still pass" check ([Gas Town architecture](https://raw.githubusercontent.com/gastownhall/gastown/main/docs/design/architecture.md)). Anthropic's C compiler run let agents push straight to upstream and added stricter CI only once new features kept breaking old ones. It also kept fleet-wide coverage cheap with a `--fast` mode, where each agent ran a deterministic 1% or 10% test sample that differed per agent ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)).

This points to an inference not stated in any one source. An LLM tester answers a question about the *diff*: does this change do what the task asked? The answer rarely changes when unrelated commits land underneath it. Re-running a 5–15 minute LLM judgment on every rebase pays the highest price for the least new information. The tree-level question can be answered by deterministic gates on the integrated SHA. The LLM verdict should be reused unless the commits between the tested base and the merge base overlap the task's files or modules, which is Uber's independence test applied to Minnow's `Touches`.

## Predictable semantic conflicts belong to lints and lanes, not LLM testers

A clean textual merge does not prove a correct merge. Build and test conflicts are rarer than textual ones but harder, and existing tools mostly target the textual kind ([TOSEM 2022](https://people.cs.vt.edu/~gulzar/assets/pdf/tosem22_merge.pdf)). For agents, conflicts are common. In 33,596 agent PRs, replayed three-way merges showed textual conflicts in **41.7%** of co-active cross-agent pairs, and about 42% of the conflicts were structural (add/add, modify/delete) ([arXiv 2607.04697](https://arxiv.org/abs/2607.04697)). Minnow's multiple-Alembic-heads failure is the canonical example: every branch passes alone, and the combined state fails with "Multiple head revisions are present." The root cause is that each hardcoded `down_revision` is a guess about merge order ([Mergify](https://mergify.com/blog/alembic-multiple-heads-git-revisions)). This class is cheap to catch deterministically, and the ecosystem has three mature patterns. Django refuses to run with more than one migration leaf, and `makemigrations --check` fails in CI ([Django #29720](https://code.djangoproject.com/ticket/29720)). `django-linear-migrations` keeps a one-line `max_migration.txt` per app, so two migration-adding branches produce a *textual* conflict at rebase time instead of a semantic failure on main ([Adam Johnson](https://adamj.eu/tech/2020/12/10/introducing-django-linear-migrations/)). Mergify's `alembic-git-revisions` derives `down_revision` from git's first-add order at runtime, and it reports no multiple-heads errors in production since February 2026 ([Mergify](https://mergify.com/blog/alembic-multiple-heads-git-revisions)). Alembic itself exposes `alembic heads` for the gate and `alembic merge heads` as a last resort ([Alembic](https://alembic.sqlalchemy.org/en/latest/branches.html)).

Prevention beats detection when the planner already knows who touches what. Anthropic's 16 agents overwrote each other's fixes while all attacking one kernel build. The fix was to re-partition with GCC as an oracle, so each agent owned different failing files ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). Claude Code's agent-team guidance says each teammate should own different files ([Claude Code docs](https://code.claude.com/docs/en/agent-teams)). Cursor showed that fine-grained runtime locks scale poorly ([Cursor](https://cursor.com/blog/self-driving-codebases)). Zuul gives each project its own queue and window, so one project's failures do not throttle another ([Zuul](https://zuul-ci.org/docs/zuul/latest/gating.html)). Carrying these over to Minnow is inference, but direct: declared `Touches` become the conflict analyzer's input. Hot resources (migrations, lockfiles, OpenAPI snapshots, route registries, barrel files) get a serialized lane or are regenerated deterministically after rebase rather than text-merged. A head-count and scratch-database `upgrade head` gate runs on the integrated SHA. The final integration tester then never discovers a fact that a single shell command could have reported.

## Spec contradictions need an owner and a stall trigger, not a bigger budget

The "Build needs backend, Touches allows only frontend" loop is a textbook multi-agent failure, not a capability gap. In MAST's 1,642 annotated traces, step repetition (**15.7%**), unawareness of termination conditions (**12.4%**), disobeying the task spec (**11.8%**) and failing to ask for clarification (**6.8%**) are among the largest buckets. Giving ChatDev's CEO role final say raised success by **9.4%**, and a high-level objective-verification step raised it by **15.6%**, the largest gain measured. Prompt-only fixes were "limited and inconsistent" ([arXiv 2503.13657](https://arxiv.org/html/2503.13657)). Cursor likewise traced its biggest misdirections to vague specs and unstated dependency rules, and warned that agents "will follow instructions to the end, good or bad" ([Cursor](https://cursor.com/blog/self-driving-codebases)).

Production detectors are cheap and syntactic. The OpenHands stuck detector, on by default, fires when the same action produces the same observation 4+ times, the same action errors 3+ times, there are 3+ monologue messages, or two action/observation pairs alternate for 6+ cycles ([OpenHands](https://docs.openhands.dev/sdk/guides/agent-stuck-detector)). Magentic-One's orchestrator asks every step whether the team is looping and whether it is making progress. When its stall counter exceeds **2**, it reflects, rewrites its fact-and-guess ledger and plan, and **resets every agent's context** before restarting. Removing the ledgers cut GAIA performance by **31%** ([arXiv 2411.04468](https://arxiv.org/html/2411.04468v1)). Microsoft's Agent Framework ships the same knobs (maximum stalls before replanning, maximum plan resets) ([Microsoft Learn](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic)). ADaPT shows that decomposing a task *after* the executor fails at it beats planning everything up front by up to 28–33 points ([arXiv 2311.05772](https://arxiv.org/pdf/2311.05772)). Applied to Minnow, the builder/tester oscillation (code added, "out of scope"; code removed, "missing") is the A-B-A-B pattern. It is detectable by hashing each attempt's touched-file set and failure clause. It should route to the planner at the first repetition, not to a fourth repair attempt, because each cycle is a full build plus test.

The remaining question is how to decide without asking. Shipped tools resolve ambiguity in one of three ways. Before the build: Spec Kit's `analyze` flags unresolved clarifications and terminology drift across spec, plan and tasks, and advises against implementing until critical issues clear ([Spec Kit docs](https://www.mintlify.com/github/spec-kit/commands/analyze)). Kiro, when a property test contradicts the code, poses the three-way choice "fix the code, fix the spec, or fix the PBT" ([Kiro](https://kiro.dev/blog/property-based-testing/)), which is exactly the decision Minnow's planner must take on its own. By authority: Claude Code's team lead approves or rejects teammate plans autonomously ([Claude Code docs](https://code.claude.com/docs/en/agent-teams)). Through durable memory: Cursor's worker handoffs carry "notes, concerns, deviations, findings" up to planners ([Cursor](https://cursor.com/blog/self-driving-codebases)); Magentic-One's ledger records "educated guesses" and, when limits hit, reports a best educated guess instead of giving up ([arXiv 2411.04468](https://arxiv.org/html/2411.04468v1)); and the C compiler agents kept running docs of failed approaches ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). Factory, by contrast, halts and returns control to the user when a mission is blocked ([Factory](https://factory.com/news/missions-architecture)). ImpossibleBench's abort result (54% to 9% cheating) suggests the same exit is valuable when it routes to a planner instead of a human ([arXiv 2510.20270](https://arxiv.org/html/2510.20270v1)).

Two cautions bound the "never needs the user" goal. First, model behaviour is a moving part. Gas Town worked "brilliantly" through Opus 4.6 and "fell apart at the seams" on Opus 4.7, whose "just two more things" tic meant it never decided it was done ([Simon Willison](https://simonwillison.net/2026/Aug/4/steve-yegge/)). Cursor found Opus 4.5 stopped early while GPT-5.2 stayed focused ([Cursor](https://cursor.com/blog/scaling-agents)). Termination therefore has to be harness-enforced and model-agnostic. Second, lights-out output is unproven. Dan Shapiro's ladder places nearly everyone at Level 3, with only a handful of sub-five-person teams at Level 5 ([Dan Shapiro](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/)). StrongDM, the one public lights-off advocate, had published no outcome data by mid-2026. HumanLayer, which went lights-off in July 2025, reports that agent-built codebases struggle after 3–6 months, that about half of one-shot AI PRs need rework, and that no benchmark penalizes maintainability erosion ([HumanLayer](https://raw.githubusercontent.com/humanlayer/advanced-context-engineering-for-coding-agents/main/wsff.md)). Fast gates do not catch slow decay.

## How Minnow's five failures map to the evidence

| Minnow failure | Mechanism the evidence identifies | What the leading systems do instead |
|---|---|---|
| 2/3 of tokens were rework | Unbounded repair after the 2–3 rounds that capture most gain; LLM findings re-open work | Contract before code; fixes become planner-owned tasks; ~2–4 validation rounds per milestone (Factory). Factory's 34% fix *features* is a count, not a token share, so it is not directly comparable to Minnow's figure. |
| Fresh-context testers never converged | <10% reviewer precision, rerun instability, no fixed reference | Judge against a pre-agreed, frozen contract; executable fail-first tests; findings outside the contract are filtered or become new tasks |
| Rebases invalidated slow tests (livelock) | Naive serial queue: result tied to "current tip" | Speculative stack testing; reuse results when intervening commits are independent; deterministic gates on the merged SHA; batch + bisect |
| Spec contradictions looped to budget exhaustion | Step repetition and unclear termination; no spec owner | Stall detector on A-B-A oscillation → planner replans or amends the spec, resets contexts, logs the decision |
| Alembic heads found only by LLM testers | Predictable semantic conflict left to a probabilistic checker | Head-count lint plus scratch `upgrade head`; sentinel file or git-derived ordering; serialized lane for migration-touching tasks |

## Design principles the evidence supports

The table separates practice that a cited system actually runs from inference drawn across sources. "Sourced" means at least one production system or controlled study does or measures it. "Inference" means the principle follows from the evidence but no source tests it in this form.

| # | Principle | Basis | Status |
|---|---|---|---|
| 1 | Write acceptance criteria before code, authored by the planner or negotiated between builder and tester, and freeze them where workers cannot edit them | Factory validation contract; Anthropic sprint contracts and status-only JSON feature list | Sourced |
| 2 | Make acceptance executable where possible, and validate generated tests to fail on pre-change code | Agentless (+6.3 pts for $0.25/issue); TDFlow 94.3% with gold tests | Sourced |
| 3 | Keep some acceptance checks hidden from the builder, or read-only, and diff-guard test files | StrongDM holdout scenarios; ImpossibleBench (test modification >79% of Claude cheating) | Sourced |
| 4 | One writer per workstream; validators judge but never fix; fixes route through the planner | Cognition, Factory, Cursor | Sourced |
| 5 | Cap blind repair at about 2–3 rounds, then change the input (stronger model, new context, re-decomposition) rather than retry | Repair-round studies; Olausson et al. | Sourced (studies); cap value is inference for repo-scale work |
| 6 | Let an LLM finding reopen work only if it is blocking and in contract, ideally backed by a reproducible failing check | Cognition intent filter; SWR-Bench precision data | Partly sourced; convergence effect untested |
| 7 | Separate "does the diff do the task" (LLM, once, at the fork point) from "does the combined tree work" (deterministic, every merge) | Gas Town gate split; no system re-runs an LLM tester per rebase | Inference from sourced practice |
| 8 | Test against a speculative stack and reuse results when intervening commits are independent of the task's declared touches | Zuul, GitLab, GitHub queues; Uber conflict analyzer | Sourced for CI; applying it to LLM verdicts is inference |
| 9 | Turn predictable semantic conflicts into lints, sentinel files or serialized lanes before any LLM sees them | Django and Alembic tooling; Zuul per-project queues | Sourced tooling; lane design is inference |
| 10 | Assign disjoint file ownership in the plan rather than locking at runtime | Anthropic oracle partitioning; Claude Code teams; Cursor lock failure | Sourced |
| 11 | Detect stalls syntactically (repeat, A-B-A oscillation) and escalate to replanning with a context reset after 2–3 stalls | OpenHands thresholds; Magentic-One stall >2; ADaPT | Sourced; first-repetition trigger for costly build/test cycles is inference |
| 12 | Give one role write authority over the spec, and log every autonomous decision and deviation so later attempts inherit it | MAST CEO +9.4%; Spec Kit Clarifications; Cursor handoffs; Magentic-One ledger | Sourced |
| 13 | Replace "ask the user" with a sanctioned abort-to-planner path and a best-effort completion with recorded deviations | ImpossibleBench abort; Magentic-One best guess; Cursor error tolerance plus green pass | Sourced components; full no-human loop is inference |
| 14 | Spend expensive evaluation in proportion to task difficulty, and re-audit the harness at each model change | Anthropic evaluator made conditional; Gas Town on Opus 4.7 | Sourced |
| 15 | Run a final reconciliation pass on the integrated branch rather than demanding per-commit perfection | Cursor green branch; Anthropic strict CI after regressions | Sourced |

## Conclusion

The evidence reframes Minnow's problem. The waste is not too little verification; it is verification that produces no new information. A fresh LLM verdict on an unchanged diff, a reviewer with no contract to judge against, and a semantic check for a fact `alembic heads` already knows all cost tokens without reducing uncertainty. Every system that converges ties each check to the cheapest oracle that can answer it, and lets the expensive oracle run once against criteria fixed in advance. The other shift is that autonomy is a property of authority and memory, not persistence. A factory never needs the user when some role inside it is allowed to change the spec and must write down why. A factory that can only retry will eventually need someone to break the tie.

The limits of this evidence matter for the redesign. The production numbers (Factory's 2–4 rounds, Anthropic's $9-versus-$200, Cursor's throughput) come from vendor case studies of single projects, not controlled comparisons. The best academic repair and judging data comes from function-level benchmarks. No source measures LLM-tester flakiness inside a merge queue, or tests whether severity rubrics make iterative review converge. Minnow's own 98-task board is therefore the most relevant dataset available. The most useful next step is to instrument it: rounds per task, the share of tester findings outside the contract, and how often re-tests reversed an earlier verdict. That would test principles 6–8 directly rather than by analogy.
